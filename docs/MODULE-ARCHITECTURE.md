# Module Architecture

**Status:** Canonical product/module boundary rules. The detailed approved session, availability, reporting, and migration design is in [PRODUCT-MODULE-ARCHITECTURE.md](PRODUCT-MODULE-ARCHITECTURE.md); implementation sequencing is maintained in [TAURI-MIGRATION-PLAN.md](TAURI-MIGRATION-PLAN.md).

## Product and Session

The product is **Music Program Scheduler**. A **Scheduling Session** is the one active local project and represents exactly one institution/program and one academic term. “Project” is a user-facing synonym only, not a separate persisted entity. Session metadata is: internal application-generated UUID, institution display name, program display name, term display label, optional year/start/end dates, and created/modified timestamps. No session timezone is required yet.

Only one session/database is active at a time initially. `.mpsession` is the versioned portable archive contract; the internal SQLite schema is not the public file-format contract. Open/Restore replaces the active session after confirmation and creation of a local recovery snapshot. Selective historical import is a separate future feature. Session archives are unencrypted in v1 and may contain student educational information; handle them appropriately.

The initial product shell starts on the active-session dashboard. Session operations are owned by the product level, not repeated inside module toolbars:

```text
Music Program Scheduler
  -> Active-session dashboard (session identity + Edit/New/Open/Export)
  -> Implemented Scheduling Modules
       -> Accompanist Scheduling

      -> Performance Juries (lesson-based setup and readiness)
      -> Clinical Placements (approved workflow; implementation pending)
      -> Lesson Scheduling (instructor/student rosters, candidates, readiness, automatic optimizer)
```

The Accompanist module has its own header, return-to-dashboard control, and internal Import Lessons, Pianists & Availability, Schedule, and Reports navigation. Session actions do not remain in that module header. Performance Juries provides lesson-based setup and readiness tabs in Panels, Lesson Entries, Pianist Availability, Schedule, and Overview order; Panels is the initial view. Schedule generation remains unimplemented. Clinical Placements provides module navigation (Clinical Sites, Student Roster, Schedule, and Reports), module-owned persistence and repositories, and a complete Clinical Sites tab: Placement Opportunity CRUD, Tag Manager, and local CSV/XLSX/XLS import. Clinical Sites import is a two-phase flow: a parse/validate/preview phase that writes nothing (`clinical_sites_importer`, which is database-free), then a confirmed, atomic full replacement through `ClinicalRepository.replace_opportunities`. Tag fields must be explicitly mapped and parsed using the shared tag format; unmapped columns never become tags. The current importer still infers tag columns from unmapped fields and is a known conformance gap. Replacement reuses or creates tags without deleting any, preserves students and student tag states, clears all Clinical Placements and the schedule revision, and increments the source-data revision. The Clinical catalog and tag-state meanings remain module-owned; shared mechanisms follow [SHARED-TAG-ARCHITECTURE.md](SHARED-TAG-ARCHITECTURE.md). Time-of-day parsing and 12-hour formatting are domain-neutral shared utilities (`services/time_parsing.py` on the backend, `lib/time.ts` on the frontend); modules must consume them rather than keep private copies. The Student Roster tab provides student CRUD (Student ID and Name required, Student IDs unique case-insensitively, validated in the repository), Clinical-owned Required/Preferred/Restricted tag-state editing against the Clinical catalog (Neutral is the absence of a stored row), and a Student Roster import that follows the same two-phase model and is a full replacement of students, availability, tag states, and placements while preserving Clinical Sites and the tag catalog; import ignores availability columns. Clinical file imports share `clinical_import_common.py`. Student availability is edited with Edit Availability (in the roster Availability column, which is highlighted amber until availability is entered and shows no window count, and in the student dialog) in a shared weekly grid: `components/WeeklyAvailabilityEditor.tsx` is a controlled, module-neutral Monday–Sunday editor (left click cycles Available, Tentative, Unavailable; a drag paints one status; right click sets Unavailable) with its cell/window conversion in `lib/weeklyAvailability.ts`, and is intended for reuse by Lesson Scheduling and Tutor Scheduling. Clinical uses a 7:00 AM–9:00 PM, 30-minute grid; unmarked cells are UI-only and are saved as Unavailable (Clear Availability empties the grid and saves no windows, returning the student to not configured), and adjacent same-status cells are persisted as recurring `AvailabilityWindow` rows (never cells) through `ClinicalRepository.set_student_availability`, which counts as one source-data change (`GET/PUT /api/clinical/students/{id}/availability`). The existing Pianist Availability grid is unchanged. Validation is layered and DB-free: `clinical_candidates.py` (legal student/opportunity candidates with preference metrics), `clinical_readiness.py` (machine-readable readiness warnings), and `clinical_optimizer.py` (exact lexicographic min-cost max-flow over feasible candidates: placed count, then preferred tags, then Tentative minutes, then start minutes, then a canonical name/id order, so results are deterministic and input-order independent; capacity is enforced only here). `ClinicalRepository.generate_schedule()` refuses (`NOT_READY`) when readiness has errors, replaces only automatic placements, preserves manual and Manually unplaced decisions (manual placements consume capacity), and bumps `schedule_revision`. The Schedule tab offers Generate/Clear, a student-oriented placement table, and manual assignment/move/Manually Unplaced actions. Manual start times accept any minute; current availability, tag, opportunity-window, and capacity warnings are displayed without blocking coordinator overrides, following the approved Clinical specification. Placement Verification recalculates whether retained placements still meet current feasibility. Availability import and reports/exports remain pending. Its approved workflow and domain policy are specified in [CLINICAL-PLACEMENT-MODULE-SPEC.md](CLINICAL-PLACEMENT-MODULE-SPEC.md). Until implemented, placeholder screens must say so and must not display fake workflow state or statistics. Replacing/restoring a session returns the user to the dashboard. Export does not change navigation state.

## Module Ownership

Modules are statically registered built-in workflows, not dynamically loaded plugins. A lightweight module descriptor may provide identity/navigation, module schema versions, validation, optimizer operation, report definitions, and declared dependencies on result contracts.

Each module owns its inputs, persistence records/profiles, constraints, validation policy, optimizer, workflow, output model, and report definitions:

- **Accompanist Scheduling:** lessons, source-owned Jury Required and Pianist Required values, pianist-specific profiles/availability, workload, fit/scoring, overlap and manual-assignment policy, assignments, and accompanist reports.

- **Performance Juries:** lesson-based entries/roster, user-selected Panels (unassigned lessons auto-assigned on exact Instrument/Panel Name match when the Lesson Roster opens), one Scheduling Date per Panel, duration/break/meal configuration, date-scoped pianist Availability Windows, readiness validation, and eventual Jury-specific optimizer/reports. Jury Required and Panel selection belong to each source lesson entry, not globally to a student. The standalone scheduler is characterized in [JURY-SCHEDULER-CHARACTERIZATION.md](JURY-SCHEDULER-CHARACTERIZATION.md); its optimizer is not integrated.

- **Clinical Placements:** module-owned students and recurring availability, student tag requirements/preferences/restrictions, Clinical Tags, Placement Opportunities and capacity, manual and automatic placement decisions, validation, a typed Clinical placement result, and Clinical reports. The director-informed, approved domain rules and lexicographic optimizer contract are defined in [CLINICAL-PLACEMENT-MODULE-SPEC.md](CLINICAL-PLACEMENT-MODULE-SPEC.md). Implement a Clinical-specific optimizer; do not reuse or coerce the Accompanist or Jury optimizer.

Never create a universal optimizer, universal assignment/schedule type, giant universal Person/Student record, or one universal spreadsheet schema.

## Shared Domain and Infrastructure

Share only demonstrated cross-module concepts and mechanics: application-generated UUID Person identity (optional institutional id/email; never merge people solely by display-name match), institution/program and term metadata, time primitives, minimal location/resource identity, import parsing/mapping machinery, validation issue representation, session file handling, availability normalization, report rendering/export primitives, and result envelopes.

Keep role/profile data module-owned around shared identity. A pianist, student, faculty member, room, or clinical site must not accumulate every field used by every module.

### Availability

The shared availability value is a window with a start/end, either a recurring weekday or a dated occurrence, status (`Available`, `Tentative`, `Unavailable`), and optional import provenance. It supports multiple windows on one day and does not assume 30-minute granularity. Submission completeness is separate from status: absent windows are unknown for an incomplete horizon and derive `Unavailable` for a valid complete horizon. Same-status overlapping imported windows may be normalized/merged; conflicting-status overlaps produce a validation/review issue and are not silently merged.

Modules retain their own status meaning, scoring, owner associations, validation, and entry UI. The Accompanist grid remains available and retains current solver semantics while becoming the first consumer of shared availability infrastructure. The shared parser accepts local CSV/XLSX/XLS, normalized rows or configurable wide Forms-style rows, and rejects conflicting overlap. Accompanist adapts only 30-minute-aligned windows into existing pianist slots and records weekly completeness in an Accompanist-specific marker; no shared owner table or session foreign keys are introduced. Availability import matches by supplied Pianist ID first, otherwise by unique exact name; it may create unknown Pianists, while ambiguous name matches require review. Each accepted respondent's complete weekly submission replaces that Pianist's Availability Windows; absent Pianists remain unchanged. New IDs use numeric max-plus-one allocation, blank email, and 40 Max Hours Per Week unless email is explicitly mapped. Import CSV/XLS/XLSX exported locally from Microsoft Forms; do not add a Forms/Graph API. Imported rows become normal editable application data.

## Cross-Module Results

Modules exchange structured, versioned results through a session-level result registry rather than importing another module's optimizer or passing spreadsheets. The envelope identifies session, module, result contract/version, state (`draft`, `finalized`, `superseded`), and provenance/revisions; its payload remains module-specific.

Jury consumes the typed, versioned `accompanist.assignment-result` contract v2 using stable Person and Lesson UUIDs. Each source lesson retains its own Jury Required, Pianist Required, and assigned pianist. Accompanist owns both requirement values as source lesson data; Jury Required is editable in both modules through the same source-owned service, with no Jury-owned Boolean copy. Jury owns only the per-lesson Panel selection, each Panel's one-day Jury Date, and date-keyed Jury-Day Availability Windows. A Jury-required lesson that requires a pianist but lacks a finalized assignment is a blocking readiness problem. Jury never substitutes a pianist. Jury-Day availability is a Jury-owned, binary, closed-world input, separate from Accompanist Tentative semantics. A declaration is complete only when it contains one or more Availability Windows; empty or invalid submissions remain incomplete. A stale Accompanist snapshot blocks readiness until reviewed and finalized again.

## Reporting

Report infrastructure may be shared for field selection, validated filters, sorting/grouping, titles, preview, and local Excel/print/PDF-oriented output. Each module explicitly provides its report definitions, allowed fields, row projection, and semantics. Do not expose arbitrary SQL/database queries or build a universal report designer.

## Persistence and Platform

The existing SQLite/FastAPI service remains transitional. Use versioned schema migrations before session/schema evolution, preserve the current local data as a legacy session with no inferred term, and keep migrations/backups reversible. The `.mpsession` manifest/archive is stable; SQLite remains private implementation payload. Opening/restoring stages and validates the archive before replacing the active session.

The application must work offline and keep student data on-device. Desktop-vs-browser and local-vs-cloud are separate choices. The eventual browser version needs local session storage/file import/export and local execution; it must not depend on a vendor server. No telemetry, analytics, student-data upload, or cloud account is implied.

## Implementation Order

Follow the approved order in [PRODUCT-MODULE-ARCHITECTURE.md](PRODUCT-MODULE-ARCHITECTURE.md): versioned migrations and session archives; shared availability and reporting; product dashboard; Jury characterization (complete) and Jury data integration through finalized Accompanist results/readiness (complete); later Jury optimizer and UI milestones; then Clinical implementation following the phase sequence and approved policies in [CLINICAL-PLACEMENT-MODULE-SPEC.md](CLINICAL-PLACEMENT-MODULE-SPEC.md). The Clinical optimizer is no longer gated on gathering initial domain policy; the approved director-informed spec is authoritative.

## Lesson Scheduling Foundation

Lesson Scheduling is a separate module with Instructor Roster, Student Roster, Schedule, and Reports tabs. Foundation, Instructor Roster, Student Roster, candidate generation, readiness analysis, optimizer, automatic schedule generation, and lifecycle alignment are complete. Reports/export remain pending (see `LESSON-SCHEDULING-MODULE-SPEC.md`).

- Current persistence is module-specific (`lesson_models.py`, `lesson_*` tables): migration v12 provides instructor/student rosters, Lesson tags, placement decisions, and module state; v13 adds schedule snapshots, unplaced reasons, and revision-stamped summaries; v14 stores day and lesson-end data on decisions and removes roster foreign-key cascades so decisions survive source identity deletion. Snapshot labels preserve stale assignments for review.
- `services/lesson_repository.py` owns persistence, revision/staleness, and typed scheduling snapshot/candidate/readiness/schedule orchestration. Pure candidate generation, readiness analysis, and optimization live in `services/lesson_candidates.py`, `services/lesson_readiness.py`, and `services/lesson_optimizer.py`; Lesson-owned input, candidate, readiness, and schedule types are in `services/lesson_scheduling_models.py`.
- The optimizer accepts only feasible candidates from a matching source revision, enforces one placement per student, instructor non-overlap, effective instructor capacity, and legal lesson-time availability. Its strict lexicographic priorities are scheduled-student count, Preferred-tag matches, tentative minutes, instructor gap minutes, then a deterministic canonical tie-break. It measures gaps only within one continuous instructor Availability Window. It does not use a shared or Clinical optimizer. Clinical may allow overlapping placements; Lesson overlap is prohibited. The two optimizers keep their own objective functions and domain policies.
- Lesson intentionally follows the same user workflow as Clinical: Data Entry → Readiness → Generate Schedule → Manual Adjustments → Regenerate → Reports. It preserves manual assignments and Manually Unplaced decisions, excludes Manually Unplaced students from automatic generation, regenerates only automatic assignments, and treats preserved manual assignments as fixed capacity/overlap inputs.
- `GET /api/lesson/readiness`, `GET /api/lesson/schedule`, `GET /api/lesson/schedule/verification`, `POST /api/lesson/schedule/generate`, and `POST /api/lesson/schedule/clear` expose readiness, assignments, verification, and summary state. Manual assignment/reassignment, Manually Unplaced, and Remove Override are typed API operations. Source changes and roster replacement retain assignments and mark the schedule stale; verification reports changed feasibility without deleting assignments. The Schedule view shows assignments and warnings alongside readiness and aggregate statistics.
- Lesson stores current decisions and display snapshots in separate module-owned tables. This retains source revisions and names/times when roster identities are removed; it does not introduce universal cross-module Assignment or Schedule tables.
- Lesson catalogs, students, instructors, and placements are independent of Clinical's even when names, IDs, emails, or tag names match. No foreign keys cross module tables, no tag catalog is shared, and matching tag names create no relationship. Shared tag infrastructure is reusable; catalogs, meanings, assignment states, validation, optimization, workflows, and reporting semantics remain module-owned.
- Shared infrastructure reused: the `ModuleBase` metadata and migration registry, session re-keying by `session_uuid`, the shared `AvailabilityWindow` type with `normalize_windows` validation/merging, and (as adopted) shared tag identity, normalization, assignment mechanics, import/export parsing, validation primitives, filtering, and reporting support. Window tables and module-specific tag associations/state semantics remain module-scoped.

### Lesson Instructor Roster

- API: `routers/lesson.py` (`/api/lesson`) with schemas in `lesson_schemas.py`: instructor CRUD, `PUT /instructors/{id}/tags`, recurring availability, Lesson tag CRUD (delete reports affected instructor/student counts), and the import endpoints.
- Instructors have name (required), email, room, Lesson Length (default 60, > 0), and Capacity (default 1, > 0). Tags are uppercase-normalized and case-insensitively unique; unused tags are greyed in the Tag Manager, and deleting an in-use tag warns first. Tags are Lesson-owned only.
- Revisions: the repository owns them. Instructor CRUD, tag changes, availability edits, and imports each call `record_source_change` once, which increments `source_data_revision` and marks an existing schedule stale. The instructor edit dialog saves fields and tags in one request, so it is one revision.
- Availability: instructors use the shared `WeeklyAvailabilityEditor` (Available/Tentative/Unavailable, Mon-Sun, 7:00 AM-9:00 PM, 30-minute grid) from the row action and the edit dialog, saving recurring `AvailabilityWindow`s into module-owned `lesson_instructor_availability_windows`. A cleared grid removes all windows rather than saving Unavailable.
- Import is two-phase. Phase A (inspect, map, preview) writes nothing. Phase B (apply) re-uploads the file and re-parses it server-side with the submitted mapping, ignoring preview data; any invalid row rejects the whole import (`VALIDATION_FAILED`) and the transaction rolls back. `lesson_instructor_importer.py` is pure parsing and reuses Clinical's pure helpers (`clinical_import_common`, availability weekday parsing) without modifying them. The required tag contract is explicit mapping to Lesson tag fields and shared semicolon-separated parsing; unmapped columns never become tags. The current importer has legacy implicit handling of unmapped columns, which is non-conforming and must be replaced before the behavior is considered aligned. Blank Lesson Length/Capacity default to 60/1; repeated names only warn.
- Replacement semantics: import replaces all instructors, their availability, and their instructor-tag links. The tag registry and students are preserved. Existing placements remain attached to their original instructor UUIDs and the schedule becomes stale; no identity matching or automatic relinking occurs.

### Lesson Student Roster

- API: `routers/lesson.py`: student CRUD, `PUT /students/{id}/tag-states`, recurring availability, and `POST /students/import/{inspect,preview,apply}`.
- Students have Student ID (required, case-insensitively unique, `DUPLICATE_STUDENT_ID`), Name (required), and optional Email. Tag states (Neutral/Required/Preferred/Restricted, shown neutral/green/amber/red with a legend) use the Lesson tag registry; Neutral is the absence of a stored row. The student dialog sends fields and tag states in one request, so a save is one revision.
- Revisions: CRUD, tag-state changes, availability edits, and imports each call `record_source_change` once (the repository owns this), bumping `source_data_revision` and marking an existing schedule stale.
- Availability: the generic `LessonAvailabilityDialog` wraps the shared `WeeklyAvailabilityEditor` and is used by both the Instructor and Student rosters (same grid and save rules, module-owned `lesson_student_availability_windows`). It is reachable from the row and the edit dialog (after the student is saved).
- Import is two-phase, as for instructors: preview writes nothing; apply re-uploads, re-parses, and re-validates server-side (`lesson_student_importer.py`, pure, reusing Clinical's helpers). Roster and weekday availability are imported together; there is no separate availability import and tags are not imported.
- Replacement semantics: import replaces all students, their availability, and their tag states. Instructors, instructor availability, and the tag registry are preserved. Students are not matched against old identities. Placement decisions remain attached to their original student UUIDs and the schedule becomes stale; no identity matching or automatic relinking occurs.

### Lesson Candidate Generation

- Implemented as pure Lesson-domain logic over a typed scheduling-input snapshot from `LessonRepository`; each candidate set carries the snapshot's `source_data_revision`.
- Candidates cover only shared legal Availability Window intervals and use 15-minute starts and each instructor's configured lesson length. Lesson-owned Required, Preferred, and Restricted tag states determine candidate issues/feasibility; Tentative minutes are summed across student and instructor availability.
- Instructor capacity is included as metadata but not enforced; overlapping candidate times remain possible. Candidate generation does not assign students or perform readiness analysis.

### Lesson Readiness Analysis

- `GET /api/lesson/readiness` analyzes the repository's typed input snapshot and matching candidate set; the pure analyzer does not regenerate candidates.
- Reports revision, roster/candidate counts, `is_ready`, and grouped typed warnings with affected Student, Instructor, or Tag subjects. The Schedule view compares readiness and current source revisions, displays grouped readiness warnings, and shows assignments with current verification warnings.
- Readiness blocks empty rosters, zero capacity, invalid instructor Availability Windows, and zero feasible candidates. Availability gaps, unmatched Required tags, students without feasible instructors, and instructors unable to fit a lesson are reported as warnings.
- Implemented: readiness analysis, optimizer, automatic schedule generation, manual assignment/reassignment, Manually Unplaced, Remove Override, stale-state handling, placement verification, and Clinical-aligned regeneration.
- Deferred: student/instructor/unplaced/warnings reports and Markdown/PDF export.
